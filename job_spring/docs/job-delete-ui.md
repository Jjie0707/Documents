## 必要的数据流与理解要点

```text
GET 详情 → 点击删除 → 展开确认区并显示目标
  → 确认删除 → 获取当前会话 CSRF Token
  → DELETE /api/jobs/{id}，浏览器携带 Cookie，无请求体
  → 已验收的 Java Controller / Service 按岗位 ID + 当前用户 ID 删除
  → 204 无响应体 → 返回列表 → GET 列表读取当前结果
```

1. **确认不等于发送请求。** confirmingDelete 只表示确认区展开，deleting 才表示正在提交。
   页面确认减少误操作；登录、CSRF、数据归属和外键约束仍由 Java 后端与数据库保证。
2. **204 不返回岗位 JSON。** request 明确不解析 204 响应体，remove 不传 JSON body。
   不会因为成功响应为空而误报失败；原有退出登录的 204 同样适用。
3. **写操作互斥。** 确认中、删除中、核对中，以及状态或删除结果不确定时，编辑和状态保存暂时禁用。
   这样可以先解决当前操作，再修改同一岗位；前端禁用不是后端授权机制。
4. **错误不提前改成成功。** 403、409、503 等保留岗位与确认区，可取消或重试；
   409 显示后端的关联数据/约束冲突提示，不提供强制删除。401 清除页面身份并转登录。
   DELETE 返回 404 时隐藏旧详情，提示“岗位不存在或无法访问，请返回列表核对”。
5. **响应丢失时先核对。** 连接失败、超时或响应无法解析时标为结果不确定，暂停写操作，提供“核对删除结果”。
   核对只发 GET：200 时用服务器结果更新岗位与状态，恢复操作并要求重新确认；
   404 时隐藏旧详情，提示返回列表核对，不把它直接宣称为本次删除成功，因为 404 也可能代表无权访问。
   核对失败则继续保持不确定，可重试核对。
6. **离页不撤销已发送的删除。** active 与请求编号防止旧 DELETE/GET 响应覆盖另一个岗位，
   或在用户离开后把页面跳回列表；服务器仍可能完成原请求，需要重新查询确认实际结果。

## 本机手动检查（用户已确认通过）

1. 保持后端与前端运行，刷新浏览器。使用临时账号，新建两条可丢弃的虚构岗位，记录数量与目标 ID。
2. 打开目标详情，在删除区域点击“删除岗位”。核对公司、岗位名及不可恢复说明，焦点应在取消。
   点取消或在确认区按 Escape，记录应保留，Network 中没有 DELETE，编辑和状态操作恢复。
3. 再展开确认并点击“确认删除”。提交中控件禁用，成功后回列表，目标消失，对照岗位仍在。
   刷新列表仍一致；旧详情地址刷新后应显示无法查看。
4. 可选：限制网络速度后连续点击确认，Network 中应只有一次 DELETE；删除未完成前不能重复提交。
5. 可选：离线确认时不能显示成功，应提示结果未确认；恢复连接后点“核对删除结果”。
   岗位仍存在时重新加载并要求再次确认；不存在或不可访问时隐藏旧详情，返回列表核对。
6. 确认区保持打开，在同一浏览器另一标签退出，再确认删除，应进入登录页。
7. 如已有带关联记录的专用虚构岗位，删除应显示 409 提示并保留内容。阶段 4 尚未开放，
   无需为本次页面验收改表、关闭外键或使用真实面试记录；该分支已在独立 H2 环境验证。
8. 手机访问已有域名，检查删除区域单列、目标文本能换行、按钮可触达，完成一次虚构岗位删除和列表刷新。

只使用可丢弃的虚构岗位。物理删除没有恢复入口；密码、Cookie、Token 和真实数据不写入代码或 Git。
