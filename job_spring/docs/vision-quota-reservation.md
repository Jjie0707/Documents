## 范围和执行顺序

`VisionAdmissionService.execute(image, clientAddress, recognition)` 固定执行：完整图片校验 → `VisionQuotaService.reserve()` → 调用方传入的识别操作。当前只在测试中使用虚构受控操作，没有模型供应商、真实图片外发或新增 HTTP 入口。5.7 必须先检查模型开关/配置、通过现有登录/CSRF/单图片规则，再使用本服务，来源 IP 必须由服务端解析，不能接收前端传来的 IP。

无效图片不扣额；IP 或全站上限已满、Redis 失败、计数异常、日期已失效，都抛出固定脱敏 `VisionQuotaException`，不会执行后续操作。本内部异常未来由 5.7 的识别接口映射 HTTP 429/503，本步不添加无用途 advice 或扣额测试接口。现有图片检查不调用 Admission，仍不扣额。

预占成功后，后续操作失败不自动返还，也不自动重试。Redis 客户端未收到预占结果时，服务端可能已经计次，必须停止，不能假定没有执行。该策略可能保守多占一次，但不因不确定结果继续调用供应商。暂不做幂等请求/预占票据，重复发起属于新尝试；5.7 会加入页面重复点击保护。

## Java 文件与 Redis 原子操作

- `VisionQuotaProperties` 增加 `globalDailyLimit`（当前默认300）和 `trustedProxies`（默认空）。每日IP上限当前默认30。两类上限必须为正 int；300是项目保护值，不是供应商承诺的免费额度。
- `VisionQuotaKeyService` 生成 IP 日键和全站日键；两者使用相同 `{上海日期}` 标签。IP 摘要继续使用 HMAC，不保存原始 IP；查询和预占使用同一规范化方式，避免 IPv6 表示差异产生新桶。
- `VisionQuotaService.reserve()` 只取一次 Clock 日期，计算本日开始和次日零点，执行一个缓存的 `DefaultRedisScript<Long>`，把键名通过 KEYS、上限和时间通过 ARGV 传入。结果只有成功才返回；其余抛出明确错误，不向用户传递连接细节。
- `redis/reserve-vision-quota.lua` 承担同时检查和写入，已随 JAR 打包。使用 EXPIRETIME，需要 Redis 7 或更新；本机为 8.6.2。
- `VisionAdmissionService` 管执行顺序，Controller 不负责扣额算法；没有 SQL、Mapper 或改表。

如果 Java 分别 GET、判断、再更新，两个请求都可能看到“还剩一次”并同时通过。`synchronized` 也只能保护当前 Java 进程。Redis Lua 在服务器内执行整段逻辑，其他命令不能在其间插入，因此多个后端实例也能共用同一套检查。[Redis Lua 官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)、[Spring Data Redis 脚本执行](https://docs.spring.io/spring-data/redis/reference/redis/scripting.html)

脚本顺序：

1. 用 Redis TIME 核对当前时刻仍在请求指定的自然日，跨零点旧请求返回 `QUOTA_DAY_CHANGED`，不写旧键、不自动重试。
2. 先检查两个键类型、计数格式及范围、EXPIRETIME 是否为对应次日零点；全站计数小于当前 IP 计数也视为损坏。异常先拒绝，避免已知格式问题导致部分写入。
3. 任一额度已满便返回，两个计数都不更新。
4. 两个计数各加 1，分别用 SET EXAT 指向同一绝对零点。每次成功仍是相同过期时刻，不能成为滑动的“再过 24 小时”。

Lua 的原子性是“不被其他请求穿插”，**不等于出现运行错误会自动回滚**。本实现把可预见的检查放在写入前；内存/故障导致未知或部分预占时，Java 停止调用且不自动补偿。计数上限是 int，脚本将异常大计数拒绝，避免 Lua 浮点精度问题。

TTL 是键距离到期的剩余时间。Java 传次日零点的绝对时间，Redis 到期删除键；日期隔离新的计数桶，过期负责清理旧键。GET 查询既不计次，也不续期。

## IP 与可信代理

`VisionClientIpService.resolve()` 先对连接来源做数字地址规范化，只接受 IPv4/IPv6，不解析主机名；拒绝带端口、括号、zone id、非法 IPv4 等输入，避免 DNS 查找和人为拆桶。IPv4 映射 IPv6 与普通 IPv4 使用同一身份。

默认 `trusted-proxies: []`，忽略 X-Forwarded-For/Forwarded/CF-Connecting-IP，使用连接 IP。`server.forward-headers-strategy=none` 保留原始连接来源。

只有直接连接方匹配配置的 IP/CIDR 时，才读取单个 X-Forwarded-For 请求头；整条链先做格式校验（不超过 1024 字符/16 跳），再从右向左剥离可信代理，取第一个不可信地址为客户端。不信任最左侧任意值，也不混用其他来源头。重复/空/坏链、全为可信代理、错误 CIDR 均停止识别；禁止 `/0` 全网信任。

以下仅为虚构配置示例，必须根据实际代理拓扑确认，不能照抄为本机 Tunnel 配置：

```yaml
vision:
  quota:
    global-daily-limit: 300
    trusted-proxies:
      - "192.0.2.10/32"
```

也可用 `VISION_QUOTA_GLOBAL_DAILY_LIMIT` 设置全站上限，配置放服务端本机文件或环境。可信代理使用 Spring 配置绑定列表。

**信任代理地址还要求入口受控**：代理须覆盖/正确追加来源头，且外部请求不能绕过代理直接访问后端。把回环或大段私网地址加入信任，并不会自动让其中所有程序可信；同机客户端仍可伪造头。用户的 Tunnel/Vite 目前保持默认保守配置，可能共享代理 IP；本轮没有读取或修改 Tunnel、私密配置，也没有宣称真实域名取 IP 已完成部署验收。

## Redis 运行边界

本机 Redis 6379 沿用用户正在运行的实例，本轮没有向它写测试计数、读取私有配置或重启它。集成测试通过 ProcessBuilder 创建随机端口、仅监听 127.0.0.1 的独立 Redis，关闭持久化，结束后停止自己的进程；只清理该独占实例业务前缀的键，不使用 FLUSHDB。

已有 Redis 的数据清空、淘汰或无持久化重启会丢失日计数，程序无法从完全丢失的键恢复真实调用量。真实模型启用前必须配置专用存储、适当持久化和 noeviction，并明确恢复期间关闭识别；不能继续把 5.5 的临时无持久化启动方式当作上线限额保障。本轮不自行改变用户 Redis 的运行策略。完整部署仍属于后续阶段。
