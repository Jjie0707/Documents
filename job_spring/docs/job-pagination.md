Mapper 的小段分页 SQL 使用现有 MyBatis 能力，便于看清数据库如何取页；本次没有引入分页插件。

```text
页面提交已生效筛选 + page + size
 → GET /api/jobs?keyword=Java&status=INTERVIEWING&page=2&size=10
 → 登录校验 → MVC 绑定与校验 JobListQuery
 → Controller 从身份中取 userId
 → Service 构造当前用户 AND 状态 AND（公司 OR 岗位 OR 城市）的条件
 → selectCount：计算该条件下全部匹配数量

 → selectPageRows：相同条件 + ORDER BY id DESC + LIMIT/OFFSET
 → 转成 JobResponse → 返回分页对象 → 页面展示本页与翻页按钮
```

## 当前接口约定（替代旧列表数组响应）

`GET /api/jobs` 当前返回对象，旧文档中的数组例子作为历史记录，详情及写入接口响应不变。

```json
{
  "items": [],
  "page": 1,
  "size": 10,
  "total": 0,
  "totalPages": 0
}
```

- page 从 1 开始，缺省或空串使用 1；必须是 Integer 范围内的大于等于 1 的整数。
- size 缺省或空串使用 10；合法范围 1～50，页面只提供三个常用选项。
- 0、负数、小数、超范围数字、非数字返回 400 和对应 fields.page / fields.size 固定提示；不回显原输入与内部异常。
- total 为当前用户在当前筛选条件下的全部匹配数，不是本页条数；items.length 为本页条数。
- totalPages 为向上取整后的页数；没有匹配时 total=0、totalPages=0、page=1、items=[]。
- 请求页超过末页，返回末页，并在 page 中返回实际页码；前端使用服务端确认值。
- 列表继续 ID 倒序、Cache-Control:no-store，未登录 401；GET 无需获取 CSRF Token。
- keyword 和 status 原有规范保持不变；传入 userId 不能切换归属。

这是响应结构变更：后端重启后必须同时刷新新前端，旧前端按数组读取无法适配；本次已同步修改页面和相关测试。
此前手写 HTTP 文件没有新增或重写，旧断言若读取数组需参照本页改为 items。

## 你需要重点理解的 Java 代码

### 1. 查询 DTO 与响应 DTO 各自描述边界

JobListQuery 接收 page/size，使用包装类型 Integer，使“没有提供”可先表示为 null，再在 compact constructor 中设默认值。
@Min/@Max 约束合法范围，格式转换失败与约束失败都返回 400。默认值只用于缺省输入，不会把非法输入静默改成合法值。

JobPageResponse 明确暴露五个字段，不直接向前端返回数据库实体或框架分页对象。
items 仍由 JobResponse.from 转换，内部 userId 不暴露；List.copyOf 固定响应列表，避免后续代码意外修改它。

### 2. 先 COUNT，再取当前页

重点看 JobReadService.listForUser。筛选条件只构造一次，统计和取页共同使用，避免“总数按全部岗位算、列表却只查面试中”这种不一致。
COUNT 之前不加排序；取页时再增加唯一 ID 倒序，保证在数据不变时跨页顺序稳定。

```java
long totalPages = total / size + (total % size == 0 ? 0 : 1);
long offset = (page - 1L) * size;
```

例如 25 条、每页 10 条，一共 3 页；第 2 页 offset=10，跳过前 10 条，再取最多 10 条。
`1L` 让计算使用 long，避免先做 int 乘法发生溢出。总数与总页数也使用 long。
先把超出末页的请求修正到末页，再算偏移量；空结果不继续执行取页 SQL。

### 3. Mapper 的 #{...} 与 ${...} 不相同

重点看 JobMapper.selectPageRows：

```sql
SELECT * FROM job_applications ${ew.customSqlSegment}
LIMIT #{limit} OFFSET #{offset}
```

`#{limit}`、`#{offset}` 和 Wrapper 中的筛选值都转成参数绑定。
`${ew.customSqlSegment}` 是 SQL 结构替换，只允许 Service 用固定列、固定操作与固定排序构造的 Wrapper，
绝不能让前端提交一段 SQL、字段名或排序片段放进这里。关键词仍通过既有 apply 的参数占位绑定，不能拼进 SQL 文本。
这是本次最需要区分的安全边界。相关规则参见 [MyBatis 参数说明](https://mybatis.org/mybatis-3/sqlmap-xml.html)
与 [MyBatis-Plus 自定义 Wrapper SQL](https://baomidou.com/guides/wrapper/)。

分页 SQL 针对当前 MySQL，以及测试使用的 H2 MySQL 模式；以后更换数据库方言时需要核对。
唯一排序保证静态数据下的顺序，不代表多次翻页是同一个快照。翻页期间如果有人新增或删除记录，OFFSET 的位置和总数可能变化；
COUNT 与取页也是两条查询，本次没有增加跨查询快照保证。大数据量的深分页可在后续学习游标分页时再优化。

### 4. 服务端校验不可依赖页面

即使页面只提供 10/20/50，手工请求仍可能提交 size=100000 或 page=-1。
后端必须校验上限、正数、整数格式；JobReadExceptionHandler 为 page/size 返回固定提示，避免内部转换消息泄露输入或实现细节。
用户归属仍来自 Controller 的 @AuthenticationPrincipal，不能交由页面参数决定。

## 必要的前端数据流

- 搜索或回车提交关键词、状态，并回第 1 页。重置清空两项筛选并回第 1 页，保留每页条数。
- 翻页和切换条数都沿用最近提交的筛选条件，不提交输入框里的新草稿；切换条数立即查询第 1 页。
- 请求时保存本次页码与条数；成功后用后端返回的实际 page、total 等展示，不能用 items.length 猜总数。
- 失败隐藏结果和翻页区域，显示失败条件与请求页码；重新加载重试原筛选、页码和条数。
- 加载时禁用条数选择并隐藏翻页按钮，防止重复翻页；仍允许搜索新条件或重置。
- 既有请求编号继续保护结果，新搜索先返回时，晚到的旧翻页响应不能覆盖它。
- 条件、页码、条数保存在列表组件内；刷新或离开列表再返回，恢复无筛选、第 1 页、每页 10 条。
