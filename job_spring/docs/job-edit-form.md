## 必要的数据流与理解要点

```text
详情 → 编辑基本信息 → GET /api/jobs/{id}
  → 从响应中取四个字段放入表单，null 显示为空字符串
  → 用户修改表单草稿
  → 提交前做必填/长度提示
  → put 获取当前会话 CSRF Token
  → PUT /api/jobs/{id}，只发送四个字段，浏览器携带 Cookie
  → 已验收的 Java Controller / Service 校验、限定归属更新、回读
  → 成功后返回详情 → GET 读取服务器内容
```

1. **表单草稿与服务器值分开。** job 保存加载到的岗位，form 保存输入中的四个字段。
   hasChanges 比较它们，只用于决定是否允许保存，输入时不直接修改详情或写数据库。
   返回页面或刷新会放弃未保存草稿，本次没有自动保存和离开确认。
2. **PUT 提交完整四字段目标值。** 即使只改公司名，也发送当前岗位名、城市、薪资。
   后端将选填空字符串规范化成 null 并实际清空，前端不能把空字段省略后期待保留旧值。
   不发送状态、userId 或其他业务字段；数据归属仍由后端登录身份及 SQL 条件保证。
3. **前端校验改善交互，Java 校验是最终约束。** 页面做必填和 Unicode 码点长度检查，
   对字段错误添加 aria-invalid，并聚焦首个出错输入；后端返回的 fields 也按字段显示。
4. **普通写请求不消耗 Token。** put 与 post、patch 共用获取当前有效 Token 的封装。
   每次提交前 GET 是现有调用策略，不代表每次都生成新 Token；登录与退出后需要重新获取。
5. **错误与保存结果分开处理。** 400 字段错误、403 和 503 保留草稿，显示提示并允许重试；
   401 清除页面身份并跳登录，404 隐藏旧表单。连接失败、超时或响应无法解析时，保存结果可能不确定，
   暂停继续提交，并提供“重新加载已保存信息”。该按钮会用服务器内容替换表单，界面有明确提示。
6. **离开页面不撤销已发送的更新。** active 与请求编号防止旧 GET/PUT 响应覆盖新页面或把页面跳回旧岗位。
   本次没有在服务器实现撤销、乐观锁或多端冲突检测；同一用户同时编辑同一字段时，以后执行的更新为准。

## 本机手动检查（用户已确认通过）

1. 保持后端运行、前端开发服务启动。使用临时账号和虚构岗位，先把状态设为“面试中”，记录岗位数量。
2. 详情点击“编辑基本信息”，确认四个字段预填正确，未修改时“保存修改”禁用。
   直接刷新编辑地址也应能加载；未登录访问应进入登录页。
3. 修改草稿后点取消，再进入编辑，确认没有保存；返回详情也不保存。
4. 公司名填空白、岗位名留空或输入超长内容，检查字段提示和焦点，失败时不应发出 PUT。
5. 修改公司和岗位名，清空城市、薪资，保存后应回原岗位详情。确认名称已更新、城市薪资为“未填写”，
   原投递状态不变，岗位数量不增加。刷新详情、返回列表再进入，内容仍一致。
6. 可选：用开发者工具限制网络速度，检查保存中输入/保存/取消/页内返回禁用；连续点击只发送一次 PUT。
7. 可选：离线提交时不能显示保存成功，应提示结果未确认。恢复连接后点击重新加载，核对实际服务器内容。
   重新加载会替换草稿，不能根据连接错误推断后端一定没保存。
8. 编辑页保持打开，在同一浏览器另一标签退出账号，再回编辑页保存，应跳回登录页。
9. 用不存在或不属于当前账号的测试岗位 ID 访问编辑页，应显示无法访问，不出现可提交表单。
10. 手机访问现有域名，确认表单单列、内容不横向溢出，完成一次保存与刷新回读。

只使用虚构岗位与临时账号；密码、Cookie、Token、真实用户或岗位信息不进入代码或 Git。
