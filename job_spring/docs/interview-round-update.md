## 页面、接口与字段规则

每页轮次下增加“编辑本轮”。展开后预填这条记录的五个字段，取消不保存。
保存成功后仍是原记录 ID；若轮次编号改变，按 ID 重新定位到新排序位置，不增加记录数量。

```text
PUT /api/interview-rounds/{id}
```

请求为完整五字段目标值：roundNo 必填；interviewTime、roundType、result、review 选填。
类型、字符数、年份、上海本地时间与毫秒精度沿用[新增轮次](interview-rounds.md)。
**选填字段缺省、null 或文本空白都表示清空原值，不表示保持不变。**
页面发送当前全部五字段；日期输入保留秒/毫秒，不因只修改复盘而截断原时间。

- 200：保存成功，返回 InterviewRoundResponse，包括重复提交相同值，Cache-Control: no-store。
- 400：字段/时间/路径 ID/JSON 格式不合法。
- 401/403：沿用登录与 CSRF 保护；有效匿名 CSRF 后仍需登录，缺少 Token 可能先返回 403。
- 404 + ROUND_NOT_FOUND：轮次不存在或属于其他用户，响应完全相同。
- 409 + DUPLICATE_ROUND：把编号改成同岗位已有编号，本次全部修改拒绝，不覆盖任一记录。
- 其他完整性错误为通用 409；其他数据库访问异常为固定 503，不暴露内部异常。

不允许修改 id、userId、jobApplicationId、创建时间等字段；多余 JSON 字段忽略，不能移动记录到别的岗位。
保持当前编号时允许修改本条内容，包括历史已有同号的情况；更换编号时必须使用该岗位未占用的编号。
因此用户可以逐条整理历史重复记录，不会自动删除、合并、隐藏或重编号。

## 文件与后端执行顺序

- common/UpdateInterviewRoundRequest.java：独立编辑 DTO，复用字段级反序列化器，明确 PUT 清空语义。
- controller/InterviewRoundUpdateController.update：接收路径、@Valid JSON 与 @AuthenticationPrincipal 身份，返回 200。
- service/InterviewRoundUpdateService.updateForUser：归属查询、父锁、当前读、改号检查、显式更新和回读。
- mapper/InterviewRoundMapper.selectOwnedRoundForUpdate：按记录 ID + 当前用户 ID 当前读，防止使用等待锁之前的旧内容。
- exception/InterviewRoundNotFoundException：区分“轮次不可访问”与“岗位不可访问”。
- advice/InterviewRoundExceptionHandler：覆盖新 Controller，沿用固定错误出口。
- frontend/src/api.js：ApiError 新增可选 code 字段，保留原 status/message/fields；让页面识别 ROUND_NOT_FOUND。
- frontend/src/components/InterviewRoundsPanel.vue：保存 editRoundId，复用五字段表单和既有 put 封装。

```text
编辑本轮 → 用当前已加载记录预填（绑定其 ID，不绑定页码）
 → 获取当前 CSRF Token → PUT 五字段
 → Security 校验 → Jackson 转换与 DTO 规范化 → @Valid
 → Service 开启事务，先按记录 ID + 用户 ID 查到所属岗位
 → JobMapper.lockOwnedJob：锁所属岗位，与新增统一锁顺序
 → selectOwnedRoundForUpdate：重新读取当前记录并确认归属/岗位没有变化
 → 若编号变化，查重；冲突则抛业务异常并回滚
 → UPDATE WHERE id=? AND user_id=? AND job_application_id=?，SET 五个字段
 → 按当前用户回读、转响应 DTO → 200
 → 页面 GET 带 roundId 定位新页，显示数据库保存的结果
```

### 为什么先查所属岗位，再锁定后重读

PUT 路径只有轮次 ID，不能信任客户端另传岗位 ID，所以先按身份查出所属岗位。
这次查询仅用于找父记录；等待岗位锁期间内容可能变化，因此取得父锁后再用 FOR UPDATE 当前读确认目标。
若直接拿第一次读取的 roundNo 决定是否查重，可能在并发改号后做出错误判断。
新增与编辑都遵循“父岗位锁 → 轮次检查/写入”的顺序，避免互相绕过查重。

### 为什么只在改号时查重

当前记录的编号本来就属于自己，保存相同编号不是新增第二条。
历史已有重复编号时，用户也应能先整理当前一条的复盘，再逐条改号。
当目标编号与当前数据库编号不同，才检查其他记录是否已占用。检查和更新都在父锁持有期间完成。

### 为什么使用显式 SET 与回读

LambdaUpdateWrapper 明确限定归属并列出五个可改字段。
.set(InterviewRound::getReview, null) 等调用会真正写 SQL NULL，允许清空选填字段。
不能依赖默认实体更新策略跳过 null，否则页面清空后数据库可能仍保留旧值。
不按影响行数 0 判断不存在：MySQL 更新相同值可能影响 0 行，但记录依然存在。
当前读确认目标、持锁更新、再回读，保证重复提交相同内容也可以正常成功。

事务与父锁保证本流程的原子修改和编号检查，不提供版本号冲突检测。
同一用户多端同时编辑同一记录时，后执行的更新为准；直接 SQL 或绕过父锁的新写入流程不受当前业务查重保证。
数据库唯一索引仍未新增，现有历史重复记录和外键 RESTRICT 继续保留。

## 必要的前端行为

- 编辑时保存记录 ID，禁用翻页/其他轮次编辑；页面草稿不会直接改变已保存卡片。
- 取消丢弃草稿不发送 PUT；保存后 ID 与总条数不变，改号会重新排序并定位。
- 字段错误/409/503 保留草稿；重复改号时刷新原记录所在页并提示，不自动改号或重发写请求。
- 保存期间输入/取消/翻页/岗位编辑/状态/删除互斥，函数入口防重复提交。
- PUT 成功但 GET 失败时保留“已更新”提示，重试只 GET；不会因为列表失败再 PUT。
- 连接失败、超时或响应损坏标记结果不确定：继续锁住写操作，GET 按目标 ID 定位核对，成功后由用户点击恢复。
- 核对失败不能恢复写操作；不确定状态允许只读翻页，方便检查记录，但不等于撤销或终止先前写请求。
- ROUND_NOT_FOUND 关闭旧编辑表单并刷新轮次，不直接隐藏仍可访问的岗位。岗位 404 沿用原处理；401 跳登录。
- 页面刷新/离开丢弃草稿，不撤销已发出的请求；旧组件 active 与请求编号继续防止迟到响应污染新岗位。
