## 当前行为与接口

- `DELETE /api/interview-rounds/{id}`：删除指定轮次及其问题记录，保留岗位、其他轮次与其他用户数据。目标是记录 ID，不是 roundNo，因此历史同号记录可逐条删除。
- `DELETE /api/jobs/{id}`：自动删除该岗位的问题、全部轮次及岗位，用户无需先逐轮删除。
- 问题记录中的问题、回答要点、知识主题和复盘随记录一起删除；删除交付时仅添加关联清理 Mapper；后续[新增/查看问题](interview-questions.md)已开发完成待验收，沿用同一表和清理方法。
- 两类删除均沿用物理删除，没有回收站。确认区明确显示目标、关联范围和不可恢复说明。
- 需要登录与有效 CSRF；不需要请求体。用户 ID 只取 Security 当前身份，查询参数或 JSON 不能切换归属。

| HTTP 状态 | 当前含义 |
| --- | --- |
| 204 | 成功，空响应，Cache-Control: no-store |
| 400 | ID 非整数或超过 Long 范围 |
| 401 / 403 | 登录或 CSRF 保护；沿用既有 Security 响应 |
| 404 | 不存在、重复删除或越权统一响应；轮次为 ROUND_NOT_FOUND |
| 409 | 完整性约束冲突，整笔事务回滚；普通面试关联数据已可自动清理 |
| 503 | 其他数据库访问失败，返回通用提示，不泄露底层异常 |

## Java 执行顺序与设计

单轮：Security → InterviewRoundDeleteController.delete → InterviewRoundDeleteService.deleteForUser → 查本人轮次获取父岗位 → lockOwnedJob → selectOwnedRoundForUpdate → InterviewQuestionMapper.deleteForRound → 删除本人指定轮次 → 204。

岗位：Security → JobDeleteController.delete → JobDeleteService.deleteForUser → lockOwnedJob → InterviewQuestionMapper.deleteForJob → 删除本人该岗位全部轮次 → 删除本人岗位 → 204。

Controller 只负责路径、身份和响应；Service 负责权限、锁、删除顺序和事务；Mapper 负责 SQL；Advice 统一转换错误。沿用现有 package，不新增通用删除框架。

两个 Service 的 `@Transactional` 将全部 SQL 放进同一个事务。保持数据库 RESTRICT，业务按“问题 → 轮次 → 岗位”从子到父删除，任一步异常都回滚；没有修改生产 SQL 或切换 ON DELETE CASCADE。

所有 SQL 限定当前用户和目标岗位/轮次，岗位归属检查必须在任何子记录删除之前。单轮首次读取只为定位父岗位，拿到父锁后重新当前读轮次，避免锁等待期间目标变化或消失。复用新增/编辑的“先锁岗位，再操作轮次”顺序，使同岗位写入和删除串行协调；不靠先数子记录再删除。

`InterviewQuestionMapper` 只有两个清理方法；`#{...}` 绑定参数，岗位范围通过所属轮次子查询取得。轮次表不删除其他岗位的记录，历史重复编号也不批量清理。

## 页面数据流

轮次卡片“删除本轮” → 展开目标确认、默认聚焦取消 → 确认才发 DELETE → 204 后重新 GET 分页。删除末页自动回新末页，最后一轮删除后显示空态，不自动改其他轮次编号。

取消或 Escape 不请求删除并恢复焦点。确认、提交、核对期间禁用冲突写操作；函数入口同时防连点。403/409/503 保留确认便于取消或重试；404 刷新列表。删除成功后列表加载失败保留成功提示，仅重试 GET。

连接失败或响应无法解析时保留目标、锁定写入并显示“核对轮次删除结果”。核对只 GET，并按 roundId 定位：仍存在则重新确认；不存在则更新列表，不能宣称一定由本次请求删除。核对失败继续锁定，不自动重发 DELETE。

岗位删除沿用原确认/取消和结果不确定时 GET 核对流程；本次更新文案为“岗位及其全部面试记录”，成功返回列表重新查询。
