# 阶段 4 后续任务：轮次删除与岗位关联记录清理

2026-10-22，用户明确要求：后续补上面试轮次删除；完成后，删除岗位应自动清除该岗位的面试记录。
**状态：已确认的后续需求，尚未实现。** 本轮只记录要求，没有修改业务代码、数据库结构或用户数据。
分页与轮次编辑仍沿用其独立验收状态，不因本次讨论而自动标记通过。

## 实施顺序与行为

1. 实现 DELETE /api/interview-rounds/{id} 与对应网页确认操作：删除指定轮次，同时清理该轮的问题记录，保留岗位及其他轮次。
2. 随后调整 DELETE /api/jobs/{id}：用户在确认区确认删除岗位后，后端自动清理该岗位的问题、面试轮次及岗位本身；用户无需先逐轮手动删除。

“面试记录”包括轮次及其问题、回答要点、知识主题和复盘内容。
轮次以记录 ID 为目标，历史同号记录可逐条删除，不能因轮次号相同误删其他记录。
删除岗位时只清理该岗位的关联记录，不涉及其他岗位或其他用户的数据。
现有物理删除语义保持，没有回收站；页面确认区应明确展示目标与关联删除范围。

## 后端设计约定

- 沿用现有 controller/service/mapper/common/advice 职责、登录身份、CSRF 和统一错误响应。
- 两类删除均在 Service 的一个事务中完成；失败整体回滚，不留下部分删除状态。
- 轮次删除顺序：问题 → 目标轮次。
- 岗位删除顺序：该岗位的问题 → 该岗位的所有轮次 → 岗位。
- 保留数据库 RESTRICT 外键，通过业务代码有序删除，不直接切换成数据库 ON DELETE CASCADE。
- 复用父岗位锁顺序，与现有新增/编辑协调并发；每一步 SQL 必须限定当前用户及相应岗位/轮次范围。
- 不存在或越权统一返回 404；删除他人岗位/轮次之前不能先删除任何子记录。
- 删除成功返回 204；单轮删除后重新获取分页并修正末页，岗位删除成功后返回岗位列表。
- 沿用响应丢失时的只读核对方式，不能把网络失败直接当作删除未发生。

## 实施时必须验证（计划，尚未执行）

- 单轮及其问题删除成功，岗位、其他轮次与其他用户记录保留。
- 岗位删除自动清理全部所属轮次/问题；无关联记录时仍可正常删除。
- 外键 RESTRICT 保持，事务任一步失败时全部回滚。
- 未登录、CSRF、非法 ID、重复删除、越权与伪造 userId 的边界。
- 真实事务并发下新增/编辑与删除正确协调，不误删、不留下悬空记录。
- 分页末页调整、确认/取消、重复点击、网络结果不确定、桌面与手机页面。
- 优先使用隔离 H2 和虚构数据，不为开发测试删除用户 MySQL 的现有记录。

当前实现仍会拒绝删除有关联轮次的岗位；只有上述后续任务完成后，才切换为用户本次要求的关联清理行为。
